# writing-skill

## 1. 这个 skill 解决什么问题

大多数“文档”失败不是因为写得不好看，而是因为**不可核验**：读者看完不知道结论从哪来、怎么复现、错了改哪里。
writing-skill 把文档当成**可测试的交付物**：每条结论都有出处，每段流程都能照做，每个验收项都能打勾。

一句话：**文档的读者不是来欣赏的，是来核对和执行的。**

## 2. 何时使用 / 何时不用

**使用：**

- 开发文档、架构文档、设计说明、接口契约、交付说明、PR 描述、事故复盘；
- 任何“别人要按它验收或接手”的文字；
- 需要向负责人/评审人证明“这事确实做成了”的场合。

**不用：**

- 宣传文案、招聘 JD、产品营销页（它们的目标是说服，不是核验）；
- 一次性聊天回复（直接说结论即可）；
- 需求本身还没想清楚时——先写任务拆解（见 `dev-skill`），再写文档。

## 3. 三条硬规则

### 规则一：结论先行，且结论必须带证据

文档开头 5 行内给出结论；每个结论后面跟**可定位的证据**：

| 证据类型 | 形式 | 可信度 |
| --- | --- | --- |
| A 级（直接） | `src/main/java/.../RiskGate.java:38`、命令真实输出、测试报告数字 | 最高，评审首选 |
| B 级（间接） | 运行日志片段、截图、构建产物、Git 提交号 | 中，需能定位到 A 级来源 |
| C 级（推断） | “我认为”“应该是”“大概” | 最低，必须显式标注“推断”并说明依据 |

写法示例：

> 风险分数 ≥ 70 时进入自动改写回流（证据：`RiskGate.java:34-36`，`mvn test` 输出 `Tests run: 12, Failures: 0`）。

不要写：

> 系统会对高风险内容做智能处理。 ← 无证据、无阈值、无法核验

### 规则二：结构固定，读者不用猜

任何开发文档都必须能落到下面的骨架上（章节可合并，不可缺失语义）：

1. **结论摘要**——做成了什么、当前状态、关键数字；
2. **背景与范围**——为什么做、边界在哪、不做什么；
3. **方案/架构**——整体结构图 + 模块职责；
4. **证据链**——结论 → 证据位置 → 验证方式（表格化）；
5. **操作步骤**——从零到跑通的命令，含前置条件；
6. **边界与限制**——已知问题、未覆盖场景、风险；
7. **验收对照**——逐条对照验收标准打勾。

### 规则三：可核验，读者能复现

- 命令必须**可直接复制执行**，并注明预期输出（含关键行）；
- 引用文件必须写**相对仓库根的路径 + 行号**；
- 数字必须可复算（阈值、次数、耗时），不要“很快”“比较多”；
- 涉及外部状态（数据库、第三方接口）时，写清**如何在没有该状态时复现**。

判断标准：一个没参与的人，只读文档、不问你，能否在 10 分钟内复现你的结论？不能就是没写完。

## 4. 文档骨架模板（可直接套用）

```markdown
# <文档标题>

> 一句话结论：<做了什么 + 当前状态 + 关键数字>

## 1. 结论摘要
- 结论 1（证据：<path:line> / <命令输出>）
- 结论 2（证据：...）

## 2. 背景与范围
- 要解决的问题：
- 本次范围：
- 明确不做：

## 3. 方案与结构
- 架构图（Mermaid）
- 模块职责表（模块 | 职责 | 关键文件）

## 4. 证据链
| 结论 | 证据位置 | 验证方式 |
| --- | --- | --- |

## 5. 操作步骤
### 5.1 前置条件
### 5.2 执行
### 5.3 预期输出

## 6. 边界与限制
## 7. 验收对照
```

## 5. 逐节写法要点

**结论摘要**：不超过 5 条；每条必须是“状态 + 证据”，不是“目标 + 决心”。

**背景与范围**：用“做 / 不做”两列写清边界。范围写不清，评审必然跑偏到“为什么没做 X”。

**方案与结构**：先图后表。图用 Mermaid（可 diff、可评审），表写模块职责与关键文件。图里每个节点都要能在代码里找到对应文件。

**证据链**：这是 writing-skill 的核心章节。一行一个结论，禁止合并；证据位置精确到文件与行；验证方式写“跑什么命令、看什么输出”。

**操作步骤**：从“干净环境”写起，包含克隆、安装依赖、运行、预期输出。常见坑（编码、代理、端口占用）单列。

**边界与限制**：主动写缺点。隐藏限制的文档在评审时会被当成“没想清楚”，而不是“做得好”。

**验收对照**：把验收标准原样抄下来，逐条给“满足/部分满足/未满足 + 证据”。

## 6. 语言与排版规范

- 一句话一个结论，句子不超过 40 字；
- 禁止空形容词（强大、优雅、高效），改用数字或对比；
- 术语首次出现给英文原词，如“状态（State）”；
- 代码块必须标语言；命令块与输出块分开；
- 表格优先于长段落罗列；
- 中文与英文/数字之间留空格；
- 图表编号并配一句“这张图说明什么”。

## 7. 自检清单（提交前逐条打勾）

- [ ] 开头 5 行内有结论，且结论带证据；
- [ ] 每个“因为/所以”都能在证据链里找到对应行；
- [ ] 所有文件引用都精确到 `路径:行号`；
- [ ] 所有命令都能直接复制执行，且写了预期输出；
- [ ] 关键数字（阈值、次数、用例数）可复算；
- [ ] 写明了“不做什么”和“已知限制”；
- [ ] 验收标准逐条对照，无遗漏；
- [ ] 图与代码一致（节点名、边方向逐个核对过）；
- [ ] 没有未标注的 C 级推断；
- [ ] 新人只读文档能复现主要结论。

## 8. 正例 / 反例

**反例（不可核验）：**

> 我们对内容做了风控，效果不错，高风险内容会被拦下来。

**正例（可核验）：**

> 内容风险分 ≥ 70 时进入自动改写回流，重试 2 次仍超标则升级人工（证据：`RiskPolicy.java:29-34`、`RiskGate.java:34-41`；验证：`mvn -B test`，12 个用例全绿，见 `evidence/mvn-test.log`）。

## 9. 常见故障与对应写法

| 故障 | 症状 | 修法 |
| --- | --- | --- |
| 结论没有证据 | 评审第一句就问“依据呢” | 补 `路径:行号` 或命令输出 |
| 结构随性 | 读者跳读找不到重点 | 套第 4 节骨架 |
| 步骤跑不通 | 别人复现失败 | 在干净目录重跑一遍，补齐前置条件 |
| 只写成功路径 | 上线后踩坑 | 增加“边界与限制”章节 |
| 图与代码不一致 | 评审发现节点对不上 | 图由代码生成（如 LangGraph4j 的 `getGraph`），不手画 |

## 10. 与其他 skill 的配合

- `dev-skill` 负责“怎么交付”（分支、契约、测试、PR）；本 skill 负责“怎么把交付讲清楚”。
- 交付顺序：先按 `dev-skill` 做出可运行产物 → 再用本 skill 写 `dev-doc.md` → 最后按第 7 节自检。
- 本 skill 的证据链章节，直接复用 `dev-skill` 要求的测试与运行日志，不要另造数据。

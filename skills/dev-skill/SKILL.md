# dev-skill

## 1. 这个 skill 解决什么问题

编排类代码最容易“看着能跑、其实不可维护”：状态字段随手加、节点职责重叠、分支靠 if 堆、交付时只有一句“能跑”。
dev-skill 把交付拆成**契约 → 实现 → 验证 → 交付**四段，每段都有硬性产物，缺一段就不算完成。

一句话：**先定契约，再写节点；每个出口都要有测试；交付物按固定结构给。**

## 2. 何时使用 / 何时不用

**使用：**

- 用 LangGraph / LangGraph4j 或任何状态机式框架做后端编排；
- 需要交付 PR、demo 仓库、评审材料；
- 多人协作、需要别人接手维护的流程代码。

**不用：**

- 改一行配置、修一个 typo；
- 纯前端页面（无状态流转）；
- 还在选型阶段、连“有哪些状态”都没定（先做任务拆解）。

## 3. 四段式交付流程

### 第 1 段：契约先行（写代码之前）

必须先产出 `docs/contract.md`，至少包含：

1. **输入契约**：字段名、类型、必填、约束、非法值处理；
2. **状态契约**：每个状态键的类型、写入节点、语义、默认值；
3. **终态契约**：所有可能的终止状态及其触发条件；
4. **不变量**：任何时刻都必须成立的条件（如“RETRY_COUNT ≤ MAX_RETRY”）；
5. **失败语义**：抛异常、落终态、还是重试。

验收口径：**契约里没有的状态，代码里不许出现；代码里出现的状态，契约里必须有。**

### 第 2 段：实现（图的骨架优先）

实现顺序固定，避免返工：

1. 状态类（`State`）：只放数据 + 只读访问器，不放业务逻辑；
2. 策略类（`Policy`）：阈值、打分、判定，全部外置为纯函数，便于单测；
3. 节点（`Node`）：每个节点单一职责，输入 State、输出**局部更新 Map**；
4. 门禁/条件边（`Edge`）：只做路由，不做业务判断；
5. 图装配（`Graph`）：集中声明节点与边，禁止在别处 `new` 节点；
6. 入口（`Application`）：只负责跑场景与打印，不写业务。

**硬性约束：**

- 状态不可变：节点返回新 Map，禁止原地改 State；
- 节点不吞异常：需要降级就落终态并写 `status`，不要 `catch {}` 静默；
- 循环必须有双保险：业务重试上限 + 框架递归上限（`recursionLimit`）；
- 终止节点显式：每个出口都 `addEdge(exit, END)`，不要依赖“没有出边”。

### 第 3 段：验证（每个出口一条用例）

测试矩阵至少覆盖：

| 维度 | 至少覆盖 |
| --- | --- |
| 正常路径 | 主流程一次性走通 |
| 条件分叉 | 每个分支至少一次 |
| 回流/循环 | 回流一次成功、回流次数耗尽 |
| 非法输入 | 每种校验失败一条 |
| 状态不变量 | 回流次数、终态取值 |

要求：

- 断言**轨迹（trace）+ 终态 + 关键计数**，不要只断言“没抛异常”；
- 测试名用“行为描述”，不用 `test1`；
- 必须能一条命令复现：`mvn -B test`（或等价），并保存日志到 `evidence/`。

### 第 4 段：交付（结构固定）

仓库根目录固定结构：

```
<repo>/
├── Architecture.md                 # 架构说明（自己写，不抄模板）
├── README.md                       # 快速开始
├── docs/
│   ├── contract.md                 # 契约
│   ├── dev-doc.md                  # 开发文档（按 writing-skill 写）
│   └── tasks/<任务名>.md           # 任务拆解与验收
├── skills/                         # 任务要求的 skill 文档
├── evidence/                       # 运行日志、测试报告、拓扑图
├── src/main/java/...               # 源码
└── src/test/java/...               # 测试
```

分支与提交：

- 分支名：`feat/<账号>-<主题>`，如 `feat/xxkingzyy-langgraph-orchestration-demo`；
- 提交粒度：契约 / 状态 / 节点 / 图 / 测试 / 文档，各自独立提交；
- 提交信息：`feat(scope): 做了什么`，正文写“为什么”；
- 交付时给出：分支名 + 关键文件路径 + 运行命令 + 测试结果。

## 4. 编排质量的六条判据

1. **状态最小**：状态里只放“节点之间必须共享”的数据，临时变量留在节点内；
2. **节点正交**：删掉一个节点不应导致其他节点改逻辑；
3. **策略外置**：阈值集中在一处，改阈值不动图；
4. **边可预测**：条件边只读状态、只返回路由键，不做副作用；
5. **可回放**：给定输入与状态快照，能复现同一结果（后续接 checkpointer）；
6. **可观测**：状态里带 `trace`，一眼看出走了哪条路径。

## 5. 交付自检清单

- [ ] `docs/contract.md` 先于代码存在，且与代码字段一一对应；
- [ ] 所有阈值集中在策略类，没有散落的魔法数字；
- [ ] 每个节点单一职责，且只返回局部更新；
- [ ] 每个出口都有 `→ END` 的显式边；
- [ ] 循环有业务上限 + 框架递归上限；
- [ ] `mvn -B test` 全绿，日志已存 `evidence/`；
- [ ] `mvn -q exec:java` 能跑出全部场景且结果符合预期；
- [ ] 拓扑图由代码生成（`getGraph(MERMAID)`），未手画；
- [ ] 分支名、提交信息符合第 3 段规范；
- [ ] `dev-doc.md` 已按 `writing-skill` 的三条硬规则写并通过其自检清单。

## 6. 常见反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一个“大节点”包办校验/分析/决策 | 无法单测、无法回流 | 按“校验 / 分析 / 打分 / 路由”拆开 |
| 阈值写在节点里 | 改规则要动图 | 全部挪到 `RiskPolicy` |
| 回流直接跳回自己 | 死循环、状态不一致 | 回流到“分析”，让明细与分数同步重算 |
| 校验失败抛异常 | 图外报错、无法审计 | 落 `REJECTED` 终态 + 显式 reject 节点 |
| 只测 happy path | 上线即炸 | 按第 3 段测试矩阵补齐 |
| 交付只有一句“能跑” | 评审无法验收 | 按第 4 段结构给全产物 |

## 7. 与其他 skill 的配合

- 本 skill 产出**可运行的实现 + 契约 + 测试**；
- `writing-skill` 负责把实现写成**可核验的文档**（证据、结构、可核验）；
- 两者共同构成一次完整交付：`dev-skill` 保证“东西是对的”，`writing-skill` 保证“别人能验证它是对的”。
